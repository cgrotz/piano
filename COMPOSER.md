# Piano Tutor — Composer & Accompaniment (Design Draft)

Companion to [DESIGN.md](DESIGN.md) / [ARCHITECTURE.md](ARCHITECTURE.md). Status: **draft,
open decisions marked ❓**.

**Decided (2026-11-14):** sound = General-MIDI SoundFont via a JS synth (§4); the
accompaniment **waits for the player** (§5); sync provider = **Google Drive** app data
folder (§7); build starts with steps 1–2 (sound engine + "Listen" preview). The practice mode (grading) stays as it is; this adds three
things on top of it:

1. **Composer** — arrange a library piece: add instruments, remove/mute existing parts.
   Added parts are **generated by rules** from the melody and harmony, not written by hand.
2. **Accompaniment in the player** — the "computer" plays the other parts. **The user's
   MIDI piano drives the progression**: the band follows you, it never runs away from you.
3. **Sync** (optional) — a storage provider such as Google Drive, so the library,
   arrangements, settings and progress follow the user across devices.

---

## 1. Concepts and data model

```ts
/** One arrangement of a library piece. A piece can have several. */
interface Arrangement {
  id: string;
  scoreId: string;          // the ScoreRecord it arranges
  name: string;             // "Pop band", "Strings only"
  tracks: Track[];
  harmony?: HarmonyOverride[]; // user corrections to the detected chords (later)
  updatedAt: number;        // for sync (last-writer-wins per record)
}

type Track = ScorePartTrack | GeneratedTrack;

/** A part already in the MusicXML (a staff / part). */
interface ScorePartTrack {
  kind: 'score';
  id: string;
  staves: number[];         // as in HandOption
  instrument: InstrumentId; // what the computer plays it with
  enabled: boolean;         // "remove instrument" = disable; the file is never edited
  volume: number; pan: number;
}

/** A part created by a generator from melody + harmony. */
interface GeneratedTrack {
  kind: 'generated';
  id: string;
  generator: GeneratorId;   // 'bass' | 'pad' | 'arpeggio' | 'comp' | 'drums' | 'second-voice'
  params: Record<string, string | number>; // style, octave, density, pattern…
  instrument: InstrumentId;
  enabled: boolean;
  volume: number; pan: number;
  seed: number;             // generators are deterministic given (score, params, seed)
}
```

**Generated notes are not stored** — only the recipe (generator + params + seed). They are
re-derived when the piece opens, exactly like the graded steps are re-derived from the
MusicXML today. That keeps records tiny, keeps sync conflicts trivial, and means improving a
generator improves every existing arrangement. (A later "freeze / export" writes them out as
MusicXML, see §6.)

All generators emit the same neutral event type on the score's **enrolled timeline** (the
same repeat-expanded time axis `extractSteps` already builds, in whole-note units):

```ts
interface PlayedNote { onset: number; duration: number; pitch: number; velocity: number; }
```

A `ScorePartTrack` produces `PlayedNote`s straight from OSMD's model (the same walk the
extractor does, minus grading concerns). This also gives a feature for free: **"computer
plays the left hand while I practise the right hand"**.

## 2. Harmony — the input every generator needs

Generators work from a **chord timeline**: `{ onset, duration, root, quality, bass? }[]`.

1. **Chord symbols present** (`<harmony>`, lead sheets) → use them directly; this already
   exists (`getChordPitches` / harmony extraction).
2. **No chord symbols** → rule-based analysis per harmonic slot (one bar, or half a bar in
   4/4 when the melody clearly changes chord mid-bar):
   - key from the key signature (major/minor guess from the first/last melody & bass notes);
   - candidates = diatonic triads (+ V7, secondary dominant V/V);
   - score each candidate: melody notes that are chord tones, weighted by metric strength
     and duration; existing left-hand/bass notes count heavily; penalty for non-diatonic;
     bonus for functional progressions (V→I, IV→V, ii→V) and for I at the end of a phrase
     / the final bar;
   - pick the best path over the whole piece with a small dynamic-programming (Viterbi)
     pass, so cadences and transitions are judged in context, not bar by bar.
3. The user can **correct a chord** in the composer (tap a bar → choose a chord). Stored as
   `HarmonyOverride`; small, syncable, and it fixes the detection's inevitable misses.

All of this is pure TypeScript and unit-testable without a browser, like `GradingEngine`.

## 3. Generators (rule-based)

Each generator: `(melody: PlayedNote[], chords: ChordSpan[], meter, params, seed) → PlayedNote[]`.

| Generator | Rules (first version) |
|-----------|-----------------------|
| **Bass** | Root on the downbeat; styles: *root* (whole/half notes), *root–fifth*, *walking* (chromatic/diatonic approach note into the next root), *pop 8ths*. Range E1–C3, octave chosen for the smallest leap. |
| **Pad / strings** | Sustained 3–4-note voicing per chord, **voice-led** (choose the inversion closest to the previous voicing), kept below the melody's lowest note in that span. |
| **Arpeggio / Alberti** | Broken chord in a meter-aware pattern (Alberti 1-5-3-5, up, up-down, 6/8 rolling), same voice-leading as the pad. |
| **Comp (guitar/keys)** | Rhythmic chord stabs from a pattern table per meter & style (pop, waltz, bossa, ballad). |
| **Drums** | Pattern per meter & style (GM channel 10), fill in the bar before a section change / repeat, crash on bar 1. |
| **Second voice** | Diatonic third or sixth below the melody, falling back to a chord tone on clashes. |

Musical guard rails shared by all: no note above the melody in the same span (except
drums/high pads by choice), velocity shaping by metric position, end on the tonic, rests
where the melody has a fermata/final note.

## 4. Sound — a free instrument collection

A small **`SoundOut` port** (same pattern as the `Unzip` port), so the source can be
swapped without touching generators or scheduler:

```ts
interface SoundOut {
  load(instruments: InstrumentId[]): Promise<void>;   // fetch + decode, progress events
  noteOn(ch: number, pitch: number, vel: number, when: number): void; // when = AudioContext time
  noteOff(ch: number, pitch: number, when: number): void;
  allNotesOff(): void;
}
```

Implementations:

- **SoundFont synth (recommended default)** — e.g. *SpessaSynth* (SF2/SF3 synth on Web Audio
  / AudioWorklet) with a General-MIDI SoundFont: all 128 GM instruments + drum kits from one
  file, faithful envelopes/loops, standard program numbers as `InstrumentId`. Candidate
  fonts: *GeneralUser GS* (free licence, explicitly allows use in software), *FluidR3_GM*
  (MIT per its Debian packaging). Compressed SF3 keeps the download in the single-digit MB.
- **Per-instrument sample sets (alternative)** — e.g. *VCSL* (Versilian Community Sample
  Library, **CC0**) for higher-quality acoustic instruments, played by a small own sampler.
  Better sound per instrument, but no drum kit/GM coverage and more assembly work.
- **Web MIDI output** — send the accompaniment to an external synth/keyboard. Almost free to
  implement because everything is MIDI-shaped already. (The Korg Liano itself only has piano
  sounds, so this is for other gear.)

Offline: samples are cached by the service worker (Workbox runtime cache, `CacheFirst`) on
first use, so the PWA keeps working offline once an instrument has been loaded.

⚠️ **Licences must be verified from the primary source before bundling.** The pre-rendered
"MIDI.js soundfonts" commonly used on the web carry conflicting licence statements
(MIT vs. CC BY 3.0 vs. CC BY-SA 3.0), so they are *not* the first choice.

## 5. Accompaniment: the piano drives the band

This is the core new runtime piece. It sits **beside** the grading engine and only listens
to it — grading logic does not change.

```
MIDI in ──▶ PracticeSession ──(step i completed / first note of step i)──▶ Follower
                                                                              │
                         tempo estimate (inter-onset intervals) ◀─────────────┤
                                                                              ▼
                              Scheduler ──▶ SoundOut (Web Audio clock, lookahead)
```

- `GradedStep` gains its **onset time** `t` on the enrolled timeline (already computed as
  `stepTimes` inside `extractSteps`, just not exposed).
- **Anchor:** when the user plays (the first correct note of) step *i*, the follower anchors
  score time `t_i` to "now". All accompaniment events with onset in `[t_i, t_{i+1})` are
  scheduled relative to that anchor using the **estimated tempo**.
- **Tempo estimate:** from the last few user onsets (score-time delta ÷ wall-time delta),
  smoothed and clamped (e.g. ±25 % per step), seeded from the score tempo / metronome BPM.
- **Never run ahead:** events at or after `t_{i+1}` are not played until the user reaches
  step *i+1*. If the user hesitates or plays a wrong note, the band **waits** — long notes
  (pads, bass) keep ringing, short ones simply don't happen yet. When the user arrives
  late, the band re-anchors and continues (no catching-up burst of stale notes).
- Between user notes the accompaniment **fills in** (e.g. arpeggio 8ths under a melody half
  note) at the estimated tempo — that is what makes it feel like playing with a band rather
  than triggering chords.
- Loops/bar ranges: the follower uses the session's selected range; on loop restart it
  cuts all notes and re-anchors.
- ❓ *Optional later mode:* "band keeps time" — accompaniment plays at fixed tempo with the
  metronome and the user has to keep up (needs timing grading; out of scope for now).

Latency: anchoring on the note-on and scheduling with a 20–50 ms lookahead is fine for
accompaniment; the user's own piano sound comes from the instrument, not the app.

The same scheduler with a **fixed clock** instead of the follower gives the composer's
**"Listen"** preview (whole piece, all tracks, including the piano part).

## 6. Composer UI

New screen reachable from the library (per piece: *Arrange*), lazy-loaded like the player.

- Track list: each track = name, instrument picker (grouped GM categories), generator/style
  picker, volume, mute/solo, remove. "+ Add instrument" offers presets: *Bass*, *Strings*,
  *Guitar comp*, *Drums*, *Second voice*, *Arpeggio*.
- Chord lane over the bars: detected chords, tap to correct.
- Play / stop preview (§5 fixed clock), with the OSMD score and cursor.
- Several arrangements per piece; the player gets an *Arrangement* picker (*None* = today's
  behaviour) and a band volume.
- ❓ Later: render generated tracks as extra staves (generate MusicXML for them and merge it
  into the displayed score) and **export** the arrangement as `.musicxml` / `.mid`.

## 7. Sync / storage provider

Today everything is local: scores in IndexedDB, per-piece settings and stats in
localStorage. Plan: stay **local-first** (the app must work offline and without an account),
and add an optional **`SyncProvider` port** that mirrors records to a remote store.

Preparation (independent of provider, worth doing first):
- move settings/stats from localStorage into IndexedDB records;
- every record gets `updatedAt` and deletions become tombstones (`deleted: true`);
- one store per kind: `scores`, `arrangements`, `settings`, `progress`.

**Google Drive (recommended first provider):**
- Files live in the **app data folder** (`drive.appdata` scope — Google lists it as a
  *non-sensitive* scope, so only basic OAuth verification; invisible in the user's Drive,
  no access to their other files). One JSON file per record; MusicXML as its own file.
- Browser-only auth with Google Identity Services, no backend (fits GitHub Pages). Caveat:
  without a backend there are no refresh tokens, so access tokens last ~1 h and are renewed
  silently while the Google session exists; occasionally the user may have to tap "Sign in"
  again. Needs a Google Cloud project with an OAuth client ID whose allowed origin is the
  Pages URL.
- Sync loop: on start, on focus/visibility change and every ~60 s while open: pull changes
  (Drive *changes* API), push local dirty records.
- **Conflicts:** last-writer-wins *per record*; settings merged *per field*; progress
  (best accuracy, last practised) merged by max. Two devices editing **the same
  arrangement at the same moment** is not merged — the later save wins. Real concurrent
  editing (CRDT) is deliberately out of scope; it would be far more work than this use
  case needs.

Alternatives behind the same port: **Dropbox** (PKCE in the browser incl. refresh tokens,
app folder — technically the smoothest browser-only option), **WebDAV/Nextcloud**
(self-hosted). Manual **export/import of the whole library** as a zip is a cheap fallback
worth having anyway.

## 8. Build order

Each step is testable on its own, as in ARCHITECTURE.md:

1. **Sound engine.** `SoundOut` port + SoundFont implementation + instrument catalogue,
   service-worker caching. *Test: play a C-major chord on strings, bass and drums; offline
   after first load.*
2. **Note timeline.** Expose step onset times; `PlayedNote` extraction for score parts;
   fixed-clock scheduler. *Test: "Listen" plays the imported piece correctly, repeats
   included.*
3. **Harmony analysis.** Chord timeline from symbols or detection. *Test (headless):
   known pieces → expected chords; cadences end on I.*
4. **Generators + Arrangement store.** Pure generators, IndexedDB `arrangements` store.
   *Test (headless): voice-leading, ranges, no notes above the melody, determinism by seed.*
5. **Composer UI.** Tracks, presets, chord lane, preview.
6. **Follower in the player.** Anchoring, tempo estimate, wait-don't-run-ahead.
   *Test (headless with virtual MIDI + fake clock), then on the Liano.*
7. **Sync.** Storage migration (§7 preparation), then Google Drive provider.
8. **Later:** notation for generated parts, MusicXML/MIDI export, MIDI out, "band keeps time".

Steps 1–6 are one line of dependent work; **step 7 is independent** and can be built in
parallel.
